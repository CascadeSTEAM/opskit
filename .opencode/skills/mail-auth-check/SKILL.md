## Steps

0. **Usage tracking (always, before anything else):**

   ```bash
   python3 bin/automation-ladder.py tick --skill mail-auth-check
   ```

   If the output has `"offer_upgrade": true`, tell the operator this
   skill has crossed the usage threshold and offer to codify it. Target
   selection (IaC rule): if this skill changes the state of ANY system —
   remote host or the local workstation — the codified form is an
   **Ansible playbook/role** in `ansible/`; a plain script only for
   repo/dev workflow. Offer an MCP tool under `mcp/` if a
   playbook/script already backs it. If they decline permanently, run
   `python3 bin/automation-ladder.py mute --skill mail-auth-check`
   so they are never asked again.

1. **Run the read-only checker** (it never edits DNS; announce this toolset first):

   ```bash
   python3 bin/mail-auth-check.py            # every domain in environments/<env>/mail-domains.yml
   python3 bin/mail-auth-check.py --domain example.com --no-blocklists
   python3 bin/mail-auth-check.py --status   # age and result of the last saved (scheduled) run
   ```

   No config yet? Copy `environments/example/mail-domains.yml` into the PRIVATE layer
   (`environments/<env>/mail-domains.yml`) and list the real domains, selectors and
   sending addresses. Domains and addresses are environment data: never commit them here.
2. **Explain every non-PASS in plain words, and confirm a surprise a second way before
   believing it.** Ask a second source (`dig @<authoritative-ns>`, the registrar's RDAP
   record, the provider's admin console via the `shared-browser` skill). Known trap: a local
   split-horizon resolver shows an internal view of a domain; the tool asks a public
   resolver on purpose. Ask the operator who really sends mail as the domain: SPF must list
   exactly those senders.
3. **Propose, never apply.** Present each change as: record, current value, proposed value,
   why, risk, rollback, how it will be verified. Order: SPF, then DKIM, then DMARC. Start
   DMARC at `p=none` with a report address; tighten only after weeks of clean reports.
   Wait for an explicit go. A DKIM key is generated by the mail provider's console (the
   operator clicks); you publish the exact value it shows.
4. **Apply (only after the go; a separate, human-approved step).** Use the DNS host's own
   tool. Snapshot the zone first. One record at a time. SPF must stay a SINGLE record
   (check none exists before adding). Long TXT values (DKIM) are split into strings of at
   most 255 characters.
5. **Verify every change**: the record on each authoritative nameserver AND three public
   resolvers (a just-created record can be hidden by a resolver's cached "no", up to the
   zone's negative TTL); the reassembled value equals what was meant; rerun the checker; the
   provider console shows authentication on; then a real test message to a checker
   (mail-tester.com) or any Gmail ("Show original": `spf=pass dkim=pass dmarc=pass`).
6. **Do not chase noise.** A blocklist hit on a shared provider address (for example one of
   Google's outbound servers) is not yours to fix and clears itself; mail-tester counts one
   listing twice (blocklist section and SpamAssassin rule). `List-Unsubscribe` matters only
   for bulk or marketing mail, not for person-to-person or single-recipient notifications.
7. **Record it** in the environment layer's session notes: what changed, record IDs for
   rollback, verification, what is still open. GitHub and public docs stay generic.
8. **Cadence.** Schedule the weekly check with
   `bash bin/ap.sh playbooks/schedule-mail-auth-check.yml -e mail_auth_env=<env>` (host in
   the `mail_auth_check_hosts` group; the unit fails only on a regression). Run it ad hoc
   after ANY DNS or mail change. `startsession` reports when the last run is older than 10
   days. Domain registration expiry is not checked by the tool: look it up (RDAP) when you
   audit. A fuller notification system (Matrix, email, text message) is a recorded idea in
   `docs/ideas.md`; until then a failed unit (`systemctl --user --failed`) is the alert.

## Failure handling

- Exit 5: `dig` is missing (package `dnsutils` or `bind-utils`). Exit 4: configuration
  missing or invalid; the message names the file and the rule. Exit 3 with `--status`: never
  run, or older than the limit.
- Two failed attempts at the same fix: stop and present the findings; do not try a third
  variation.
- The operator says "stop": stop. No more lookups or changes.

## Do NOT

- Edit DNS from this skill or from the checker, or apply a proposal without a clear go.
- Put real domain names, selectors or addresses in the public repo, issues or PRs.
- Read secrets: nothing here needs a credential except the DNS host's own tool at apply time.

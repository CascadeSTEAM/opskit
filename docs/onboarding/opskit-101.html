03 / 10

Every network gets its own labeled folder

OpsKit calls each network an environment — its own folder with its own devices, its own passwords, its own rules. Nothing is hardcoded, so the same toolkit works for a homelab, a client site, or a school lab without rewriting anything.

Why this matters

Real environments never touch the public code. A shared example folder shows the pattern; your actual devices, IPs, and client details stay private and local.

05 / 10

Playbooks: instructions a computer can't get wrong

A playbook is a plain-text list of steps — written once, run as many times as needed, always in the same order. No copy-pasting commands into a terminal and hoping you didn't miss one.

# a tiny slice of a real playbook
- name: make sure the web service is running
  hosts: servers
  tasks:
    - name: install nginx
      apt:
        name: nginx
        state: present
    - name: start nginx
      service:
        name: nginx
        state: started
📋 The superpower: idempotence

Run a playbook once or fifty times — it only changes what actually needs changing. That makes it safe to re-run any time you're not sure the last run finished. In OpsKit you run one through bin/ap.sh <playbook>, which scopes it to whichever environment you've switched into, so it only ever touches the network you meant.

06 / 10

You get specialist helpers, not one generalist

OpsKit plugs in AI subagents scoped to one job each — like handing the router questions to the router expert instead of a jack-of-all-trades who might miss something.

@mikrotik

Handles routers, switches, and WiFi — through a safe, approved tool path only.

@linux

Handles servers, Docker, and Ansible — router tools are off-limits to it, on purpose.

📋 Why split them up?

Guardrails, not gatekeeping — each helper can only touch what it's actually qualified for, so a mistake in one lane can't spill into another.

07 / 10

Four rules that never bend

Never assume

IPs, credentials, and roles get verified live — not remembered from last time.

Every change gets a ticket

If it touches real infrastructure, there's a helpdesk ticket number attached to it.

Repeatable work becomes code

Do something by hand twice, and it becomes a script or playbook the third time.

Document as you go

Not done until it's written down — future-you and new-hire-you will thank present-you.

08 / 10

Tickets: the paper trail for real changes

Before anything touches a real device, OpsKit wants a ticket — a short record of what you're about to do and why. It's not bureaucracy for its own sake; it's how "who changed this, and when, and why" stays answerable months later.

# open one before you touch anything live
bash bin/switch-env.sh homelab
bash bin/open-ticket.sh "patching WiFi firmware on the 3rd floor APs"
# the ticket number gets written to .current-ticket automatically
Enforced, not optional

Every commit touching live infrastructure must reference its ticket (TKT-42: fixed AP firmware) — a pre-commit hook checks for it and blocks the commit if it's missing. Read-only checks and docs-only commits are the only exceptions.

09 / 10

A typical change, start to finish

Pick the environment

Switch into the right network so every command points at the right place.

Open a ticket

State what you're about to do before you do it.

Make the change

Through a playbook or an approved tool — not a one-off manual edit.

Test it

Confirm it actually worked before calling it done.

Write it down

Update the device record so the next person doesn't start from zero.

10 / 10

Try it yourself

Five commands take you from a fresh clone to a full picture of a network.

# clone it and check your setup
git clone https://github.com/CascadeSTEAM/opskit
cd opskit && bash install.sh
opskit check

# point it at a network and look around
opskit env homelab
opskit scan
opskit status
